# 上位机界面卡顿只读审查（2026-11-01）

本次仅检查电脑端源码，并用 `QT_QPA_PLATFORM=offscreen` 和内存模拟帧做性能测量。没有连接服务或机器人，没有发送 SSH 或 CAN 指令，没有停止正在运行的上位机。没有修改业务代码或控制周期。

## 已确认的界面瓶颈

1. `desktop_motor_control.py` 的 250 ms 定时器调用 `refresh()`，检查模式下每次都执行 `populate_check_mapping()`，重新创建 24/28 × 7 个 `QTableWidgetItem`。反馈、检查采样和状态事件在 `on_event()` 末尾也调用相同 `refresh()`。
2. 映射表使用 `ResizeToContents`，在展开显示后，每次替换表格项会引发尺寸计算和布局。本任务主代理的独立复现：28 轴、60 次刷新，折叠约 5.16 ms/次，展开约 275.8 ms/次；11,760 次 `setItem` 累计约 16.345 s。单次展开刷新已超过 250 ms 定时器周期，是足以造成明显界面滞后的确定瓶颈。
3. 本审查独立测量的折叠、24 轴刷新约 2.61 ms/次（200 次）。其中 `populate_check_mapping()` 占累计时间约 94%，`start_pose_report()` 占约 64%。折叠结果较快与上条并不矛盾：展开后的同步布局是主要差异。
4. 预览接口 `preview_api.py` 每 0.1 s 发送一帧，`Reader` 每帧发出信号，主窗口 `on_frame()` 不合并、不区分页面可见性，持续更新健康页、隐藏曲线、关节表和诊断上下文。28 轴、100 帧、含 Qt 绘制的独立模拟测量：整机页约 44.4 ms/帧，切到角度页约 8.36 ms/帧。整机页中约 32.3 ms/帧落在 `processEvents()` 中的布局与绘制。测量是本机模拟负载，不能视作用户现场的精确延迟。
5. 主窗口每帧重复执行健康数据构建约 3 次，并多次设置相同样式；`app_shell.render_health()`、基础 `render_health()` 和 `operations_panel.set_frame()` 都产生相关工作。两个健康曲线即使隐藏也重新 `setData()`；已有表格项部分复用，但进程表和控制反馈表仍持续替换单元格。

## 不应误判的事项

- 没发现主窗口周期刷新在 GUI 线程同步执行 SSH、HTTP 或数据库请求。网络主要在 `QThread` 工作者中；控制窗口每次只做本地 `known_hosts.is_file()` 和缓存上下文检查。
- 角度转换确实重复验证映射并执行踝部正解。正常模拟起点的纯转换约 0.5 ms，几何不相容踝角的失败路径可约 28 ms；单凭正常转换耗时不足以解释展开表格的严重卡顿。
- 不能用减少机器人控制频率、放宽反馈新鲜度或取消停止条件解决电脑界面绘制问题。

## 建议修复范围

电脑端复用单元格、避免相同内容重复通知和 `ResizeToContents` 高频同步计算；静态映射在机型/元数据变化时生成，动态角度按反馈代次更新，折叠表仅更新必要摘要；每次事件仍保留身份/绑定失效检查及停止入口。机器人控制周期、反馈时限、力矩阈值和异常停止逻辑维持原值。
